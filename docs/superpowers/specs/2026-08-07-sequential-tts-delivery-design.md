# 多回复逐条 TTS 交付设计

## 目标

将多条 Agent 回复从“全部 TTS 完成后整批入库”改为“每条完成 TTS 后立即入库”，缩短首条消息出现时间并保持消息顺序。

## 数据流

1. LLM 返回完整 `replies` 数组。
2. 预处理纯 Emoji：附着到相邻文字回复，不保留独立纯 Emoji 消息；整批没有文字时视为无有效回复。
3. 按顺序处理每条文字回复。
4. 当前条独立合成 TTS，成功则携带音频入库，失败则立即以文本入库。
5. 当前条入库后再处理下一条。
6. 全批至少入库一条时，本轮回复判定为成功。

## Emoji 规则

- 纯 Emoji 位于文字之后时附到前一条文字。
- 开头连续纯 Emoji 附到第一条后续文字。
- 两条文字之间的纯 Emoji 附到前一条文字。
- 末尾纯 Emoji 附到最后一条文字。
- 整批只有纯 Emoji 时全部忽略。
- Emoji 只写入消息 `emoji` 字段，不参与 TTS 文本。

## 取消与一致性

- 每条 TTS 前、TTS 后和消息入库前检查协程取消与 Agent generation。
- 已入库消息不会因后续取消回滚。
- 当前及后续未入库消息在取消后停止处理。
- 通知在整批处理结束后只发送一次，使用最后一条已发送消息。

## 验证

- 单元测试覆盖纯 Emoji 的前置、中间、尾部、连续和全 Emoji 场景。
- 编译检查确认串行循环直接在每次 TTS 后调用 DAO 插入。
- 完整单元测试、Lint 和 Debug 构建通过。
